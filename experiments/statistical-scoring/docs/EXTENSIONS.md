## Follow-on Directions

This project is primarily about building a more trustworthy scoring and comparison layer for evaluator-based assessment, but that foundation also enables several important follow-on directions. In that sense, the value of the project is not limited to the initial scoring method itself. By making evaluator outputs more interpretable, more stable, and easier to compare across runs, the project creates the measurement framework needed for more ambitious evaluation workflows.

One natural extension is the use of evaluators as reward signals for reinforcement learning. A longer-term platform goal is to reuse `strands-evals` outputs as rewards during optimization or fine-tuning. However, that only makes sense if the evaluator signal is sufficiently stable, well-calibrated, and aligned with actual task quality. If the reward is noisy, coarse, or dominated by off-axis evaluators, the training process could optimize against artifacts rather than meaningful improvements. In the worst case, that could encourage reward hacking, misleading summaries, or brittle behavior that looks good to the evaluator but is not genuinely better. The work proposed in this project, especially variance decomposition, evaluator weighting, and uncertainty estimation, is therefore a prerequisite for any serious attempt to use evaluator outputs as RL rewards. A natural next step after this project would be to test whether the statistically adjusted score is stable enough to serve as a training signal and whether it improves optimization behavior relative to a plain average.

A second extension is LLM-as-a-jury evaluation. Instead of relying on a single judge output, we could evaluate each run with a small panel of judges and aggregate their decisions using a structured rule. That idea becomes much more compelling once we already have a principled way to reason about evaluator variance, replay noise, and uncertainty. This project provides exactly that language. It would let us ask concrete follow-up questions such as how much variance a jury reduces relative to a single judge, whether the gain in stability justifies the added inference cost, and whether certain evaluator types benefit more from jury-style aggregation than others. In other words, this project does not directly build a jury-based evaluator, but it establishes the statistical framework needed to evaluate whether such a system is worthwhile.

More broadly, these extensions highlight why the present work should be viewed as foundational rather than narrow. Its immediate output is a better scoring and comparison method, but its broader contribution is to turn evaluator outputs into a more trustworthy measurement instrument. That is what makes downstream uses, such as RL reward reuse, jury-based judging, and eventually CI-style gating, credible enough to pursue.

There are also several follow-on directions that sit closer to the evaluation product itself. One is support for tool-level evaluators, which emit one verdict per tool call rather than one verdict per run. Incorporating those evaluators will require deciding how call-level judgments should be aggregated before they enter the variance decomposition, since the aggregation choice will directly affect both the score and the uncertainty estimates. Another extension is paired comparison, where a baseline and a candidate agent are evaluated on matched cases and the output is a decision such as `improved`, `regressed`, or `no_change`, rather than only a raw score difference. A related need is robust failure handling, so that true low-scoring runs are distinguished from infrastructure failures, crashed runs, and empty trajectories instead of being silently folded into the same score distribution. Finally, if these pieces work well enough, the comparison result could be surfaced through the CLI in a machine-readable form that supports `strands-evals compare` and, eventually, a CI merge gate.
